# Disposable OpenBao fixture

This source is linked into test-only executables; it is not a production host/provider. It reuses the existing installer integration fixture and `LocalOpenBaoSession`. Authority: Development Docs 01 section 16, 06 sections 1/3/5/6, 09 section 2 and active P1-024-RV003. Existing P1-024-RV001 committed evidence documents the original scoped identity, exact R2 resource, CAS/reuse and cleanup behavior.

The finite coordinator generates its own bootstrap and unique namespace in memory. Application composition receives only a session's `Secrets`, then the approved credential adapter. R2 keeps its exact resource ACL and existing overload. The new trusted scope grants only descendants of a validated prefix plus a nonempty per-instance ID, never a browser-supplied path.

The fixture requires already-cached `openbao/openbao:2.7.0`; no image build/pull is performed. Image ID/version and selected non-secret Docker configuration are recorded as typed provenance. This test image is not a change to the maintained foundation image or a production/security-image acceptance claim. The cached image declares no volumes. The fixture refuses declared/runtime volumes, binds only host 127.0.0.1, disables Docker log persistence, uses `-dev-no-store-token`, and consumes no server output. No environment payload or container log is read/serialized. Resource-reaper cleanup is disabled for this one finite owned resource so no helper image/container can be pulled; explicit bounded deletion and Docker-confirmed absence are mandatory instead. No global Testcontainers setting or other project/container is changed.

The bootstrap remains private to this test coordinator and its transient container environment; it is never an application token/configuration value or host credential file. OpenBao dev storage is in memory. Test-seed retention ends only when the owned container is verified absent. Session revocation/policy removal is attempted before container deletion; every cleanup stage is attempted despite earlier failure. Any failed stage rejects cleanup success and repeated disposal cannot turn that failure into PASS. Cancellation of the test operation does not cancel cleanup.

Before generating a credential or creating a client/resource, the actual Testcontainers Docker API endpoint must be a local named pipe (`.`/`localhost`, one pipe name) or an absolute local Unix socket with no remote authority. TCP/HTTP/SSH, remote named pipes, UNC forms, user-info and query/fragment overrides are rejected with one fixed error. The validated endpoint is then explicitly bound to the container builder. Public endpoint probes exercise the real startup entry and prove invalid inputs never reach the client factory or make network calls; valid local forms reach only a controlled throwing factory.

The bootstrap APIs and `BootstrapClient` are privileged test setup only. Never register the fixture/admin client as an application service, print raw exceptions, request values, headers, environment inspection, or secret assertions/diffs. The integration tests compare secret values as booleans and preserve existing R2 assertions. The new regression also reads immutable version one after an administrative version two write and rejects sibling namespace access.

Implementation and source-bound validation are separate. Build/regression receipts must identify the committed complete source array; this file does not claim that tests or a real browser TOTP journey passed.
