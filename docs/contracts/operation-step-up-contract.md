# P2-006 private operation-bound step-up lifecycle

Authority: FRD17§§6–8/15–16; security document08§§authentication/security evidence; catalog32§§1–2/17–19; ADR-0006; AMD-0004/0005; PDR-0011/AMD-0007. This is a private Identity implementation contract, not a public Product API, new assurance policy or production configuration.

The authenticated User BFF derives Account/session/origin from its real server-issued principal and network partition from the real peer. A trusted owner supplies stable operation/correlation identity, exact resource/expected version, operation policy scope and SHA256 context digest. No browser-selected assurance, timestamps, Account, method or policy authority is accepted. User and Admin schemes remain separated.

Password reauthentication verifies the current Identity credential using the existing framework hasher and versioned authentication limits. Existing authentication abuse windows/limits and processing/retention references govern this password-authentication evidence; no defaults are introduced. Operation-specific assurance is selected at current server execution time, with exact expected policy version. Opaque assurance identifiers are not ranked; the approved operation/context method mapping must explicitly produce the required assurance. Other authenticator methods remain their future work items.

An opaque random256-bit proof is hashed for lookup and its retry secret is purpose-protected server-side. Bind Account, current session, User scheme/origin, security stamp, operation/resource/expected version/context digest, method/assurance, policy and original fresh-authentication time. Expiry cannot exceed the policy lifetime, session expiry or current policy interval. Repeated issuance for the same operation requires fresh valid credentials and identical bindings; it cannot replace or revive an ended proof.

Consumption revalidates the current session/credential/contact and Account restriction authority for the exact sensitive operation, resolves the effective policy again, and rejects wrong scope/resource/version/context/session/origin, stale policy, expiry and replay. Session/proof locks and version checks serialize competing consumption. Consumption and the Identity owner's local mutation/outbox must share the same database transaction. The internal callback must use this scoped Identity context, validate its current target expected version, perform no network/provider side effects, and preserve the owner's stable operation-result/idempotency contract. Proofs are authorization evidence, not an operation-outcome ledger. A consumed proof never authorizes another execution; unknown commit outcomes are reconciled through the owner's operation record.

Proof issuance/consumption does not alter session authentication time, assurance, cookie key or expiry. It is not a general session upgrade. Metadata/key/binding/expiry are immutable in PostgreSQL; only one-way ACTIVE→CONSUMED/EXPIRED is allowed. Ended proofs clear protected retry material. Post-commit security events carry safe proof references, never passwords, raw proof keys or personal data. Record explicit processing/retention policy references; no retention period is guessed. Expired-key cleanup is a technical lifecycle action; metadata purge remains governed by actual retention authority.

This slice enables no HTTP route or production composition. Frontend challenge/resume UX, actual Figma/content review, protected BFF operation contexts and configured approved runtime-policy evidence remain required before browser/production acceptance. Current onboarding/login behavior must remain intact. Tests use isolated disposable PostgreSQL and labelled synthetic policies; no operator database or image rebuilding.

## User BFF browser bridge

This work-item extension reuses FRD17 section7, catalog32 sections1–2/17–19, the current User BFF HTTPS/origin/CSRF boundary and current authentication browser-context lifetime. It creates no Product-facing API or new assurance/retention values.

A trusted operation-owner provider resolves the pending operation from current server-owned workflow state for the real authenticated Account/session/origin. It returns immutable original operation/correlation/resource/expected-version/context bindings, expected approved policy version, and authoritative completion state. The browser cannot choose these values. The provider applies only its Identity-local mutation and stable operation ledger through the supplied context and transaction, with no provider/network I/O.

Opt-in endpoints are GET /authentication/step-up/options and POST /authentication/step-up/password. They require the User authentication scheme and existing HTTPS/host/origin/CSRF controls. Options supplies a non-authorizing request ID, explicit password availability/maximum length, CSRF token and published content. The immutable operation/policy/view binding is purpose-protected in a Secure, HttpOnly, SameSite=Strict __Host- cookie. Its lifetime uses the existing explicit AuthenticationPolicy browser-context value and is clipped by the assurance interval. Refresh can reuse a current identical binding; it cannot extend proof lifetime or revive an ended proof.

POST accepts only requestId and password under strict bounded JSON parsing: duplicate, unknown, malformed or excessive input is rejected. It re-resolves current owner authority and policy and verifies the protected view binding, preventing a different tab or changed operation from silently authorizing another action. It issues the existing proof and consumes it on the server with the original action transaction. Neither raw proof nor password is returned, put in a URL, local/session storage or browser-visible cookie. Changing policy/context requires a new review of the owning action.

After a lost success response or competing duplicate, the owner's already-committed operation ledger is authoritative for completion reconciliation; it does not rerun the action or revive a consumed proof. Cancellation before submission applies no action. Pending cancellation is disabled; closing the browser cannot reverse a committed operation. The UI reconciles via current owner status instead of blindly repeating an uncertain mutation.

This bridge is activated only when the owner operation source, assurance policy source and published presentation source are explicitly registered on the authenticated User BFF. Default and Admin surfaces remain unactivated. Production configuration is not synthesized. Local/browser/QA fixtures are explicitly synthetic and cannot serve as production policy or Product acceptance.

The reusable dialog stays on its owning canonical screen and keeps OAuth/Product-origin state with the owner. Independent future screens require inventory/route guards. New password-detail composition and material visual states require the scoped AMD-0008 approval recorded in the browser review packet before final production UX implementation.

## Completion recovery binding

A completed options response includes requestId only when the current protected browser view matches the exact current actor/operation/policy digest and has not expired; otherwise requestId is null. A fresh owner view may show its authoritative completed status, but an already-open dialog must compare requestId with its original bootstrap identity before invoking onComplete. Another tab/session/operation completion or an expired/missing view cannot complete that earlier dialog. This status read still needs no new assurance challenge or presentation publication after the operation has committed. Password POST remains independently bound and revalidated before applying or reconciling its action.
