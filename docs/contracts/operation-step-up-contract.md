# P2-006 private operation-bound step-up lifecycle

Authority: FRD17§§6–8/15–16; security document08§§authentication/security evidence; catalog32§§1–2/17–19; ADR-0006; AMD-0004/0005; PDR-0011/AMD-0007. This is a private Identity implementation contract, not a public Product API, new assurance policy or production configuration.

The authenticated User BFF derives Account/session/origin from its real server-issued principal and network partition from the real peer. A trusted owner supplies stable operation/correlation identity, exact resource/expected version, operation policy scope and SHA256 context digest. No browser-selected assurance, timestamps, Account, method or policy authority is accepted. User and Admin schemes remain separated.

Password reauthentication verifies the current Identity credential using the existing framework hasher and versioned authentication limits. Existing authentication abuse windows/limits and processing/retention references govern this password-authentication evidence; no defaults are introduced. Operation-specific assurance is selected at current server execution time, with exact expected policy version. Opaque assurance identifiers are not ranked; the approved operation/context method mapping must explicitly produce the required assurance. Other authenticator methods remain their future work items.

An opaque random256-bit proof is hashed for lookup and its retry secret is purpose-protected server-side. Bind Account, current session, User scheme/origin, security stamp, operation/resource/expected version/context digest, method/assurance, policy and original fresh-authentication time. Expiry cannot exceed the policy lifetime, session expiry or current policy interval. Repeated issuance for the same operation requires fresh valid credentials and identical bindings; it cannot replace or revive an ended proof.

Consumption revalidates the current session/credential/contact and Account restriction authority for the exact sensitive operation, resolves the effective policy again, and rejects wrong scope/resource/version/context/session/origin, stale policy, expiry and replay. Session/proof locks and version checks serialize competing consumption. Consumption and the Identity owner's local mutation/outbox must share the same database transaction. The internal callback must use this scoped Identity context, validate its current target expected version, perform no network/provider side effects, and preserve the owner's stable operation-result/idempotency contract. Proofs are authorization evidence, not an operation-outcome ledger. A consumed proof never authorizes another execution; unknown commit outcomes are reconciled through the owner's operation record.

Proof issuance/consumption does not alter session authentication time, assurance, cookie key or expiry. It is not a general session upgrade. Metadata/key/binding/expiry are immutable in PostgreSQL; only one-way ACTIVE→CONSUMED/EXPIRED is allowed. Ended proofs clear protected retry material. Post-commit security events carry safe proof references, never passwords, raw proof keys or personal data. Record explicit processing/retention policy references; no retention period is guessed. Expired-key cleanup is a technical lifecycle action; metadata purge remains governed by actual retention authority.

This slice enables no HTTP route or production composition. Frontend challenge/resume UX, actual Figma/content review, protected BFF operation contexts and configured approved runtime-policy evidence remain required before browser/production acceptance. Current onboarding/login behavior must remain intact. Tests use isolated disposable PostgreSQL and labelled synthetic policies; no operator database or image rebuilding.
