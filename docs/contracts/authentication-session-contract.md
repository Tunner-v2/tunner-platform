# P2-005 private User BFF authentication and session contract

Derived from FRD17 §§6/8/13/15/16, ADR-0006 and catalog32; not a new Product or public OAuth contract. This is an implementation specification pending executable validation and scoped UI acceptance.

GET /authentication/options is anonymous, same-origin, HTTPS and no-store. It returns the maximum accepted password length, private operation idempotency key, framework antiforgery request token and trusted published presentation. The policy version stays in protected server-owned context rather than request JSON. It sets a purpose-protected HttpOnly/Secure/Strict host-only browser-context cookie with nonce, policy, expiry, previous authenticated session reference and digest of the previous opaque User cookie. These are server-originated and never accepted as browser policy/actor authority. Reissuing options must not extend an existing operation context silently.

POST /authentication/sign-in accepts only IdempotencyKey (nonempty Guid), Email, Password and RememberMe. It is an explicitly anonymous credential transaction requiring matching protected bootstrap and CSRF plus same-origin checks, including when the browser already has a User cookie. No return URL, AccountId, scheme, assurance, lifetime, restriction decision or policy version is accepted from request JSON. Email is normalized using the existing authoritative mechanics; credentials are verified using ASP.NET Identity V3 hashing. No registration password composition/minimum rule is applied to existing passwords. Missing/oversized/malformed fields fail before mutation. All credential/state/restriction failures use a generic safe authentication response. Trusted policy/provider failures are service unavailable, not credential acceptance.

A successful operation creates a fresh random 256-bit server lookup key and encrypted framework ticket bound to User scheme/origin, Account, security stamp, trusted policy and absolute/idle bounds. Lookup keys are stored only as SHA256 digests; replay material is purpose-protected server-side. The old browser session is revoked atomically with the new session. Duplicate successful commands require the same protected nonce, identity and verified credentials, return the same still-active result and cannot revive revoked/expired state. Different identity/content under a reused key conflicts; no password-derived request fingerprint is persisted. Trusted network/identifier abuse counters are HMAC-derived, policy-window-bound and concurrency-safe. Security stamp changes and current Account/contact/restriction authority are checked on retrieval; absolute expiry is never extended, and idle activity cannot race to resurrect revocation.

GET /authentication/session requires the User scheme and returns only authenticated=true and an antiforgery token for authorized same-origin mutations. It exposes no bearer, Account identifier, profile, policy internals or OAuth token. Unknown/expired/revoked sessions return401. POST /authentication/sign-out requires antiforgery/origin, revokes the authoritative current Tunner session idempotently and deletes its cookie; repetition by the same browser has no additional domain effect. It does not end Connected Product-owned sessions.

TunnerSession persists session id, hashed key, encrypted ticket/retry key, Account, BFF scheme/origin, methods/assurance, authenticated/last-seen/absolute expiry, idle limit, state, policy/access/security provenance, operation/correlation/version and lifecycle refs. State changes and post-commit security events use the existing transactional outbox; no email/password/bearer is put in event payloads or logs. Retention is owned by a trusted versioned lifecycle contract, not guessed here.

Authentication policy source uses EffectivePolicyVersionResolver with explicit approval metadata. Required values: version; password maximum/hash work factor; regular/remember absolute and idle lifetimes; bootstrap lifetime; abuse window/limits; password method assurance mapping; processing and retention refs. Values must be positive, coherent and fit server transport bounds. No production defaults. Current Account access decisions bind Account id and state version, operation SIGN_IN or SESSION_USE, effective time interval, policy and evidence refs. CLOSED and unverified cannot be overridden; age alone is not an access restriction. Missing/stale/ambiguous authority fails closed/unavailable. Restriction owner remains separate from this slice.

/login and /signed-in are canonical UI routes. Login is accessible anonymously and signed-in direct entry verifies the current User session server-side. Unknown paths/API methods keep existing fallback protections. No credentials, personal data, proof or tokens enter paths/query/history/storage. Client validation uses the shared typed schema/error/focus/pending system; backend validation remains independent. URLs/forms and responsive visual comparisons require their own source-bound URL/VAL/UX evidence.
