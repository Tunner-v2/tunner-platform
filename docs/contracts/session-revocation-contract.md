# Private owned-session revocation increment

Authority: FRD17 session/revocation and post-commit event contracts; catalog32 operation, event, assurance and policy invariants; ADR-0006; existing authentication/session and operation-step-up contracts. This application-only increment introduces no HTTP/UI activation, production policy values, device/trust authority or Product-session termination claim.

`SessionRevocationApplication.PrepareAsync` independently authorizes the current User actor for `SESSION_REVOKE` and validates the exact other session, same Account/origin/User scheme, expected version and effective authentication state. The trusted binding uses `SESSION_REVOKE / USER_BFF`, stable request/operation/correlation identities and a digest of the actor and target context. The existing assurance source selects the required assurance, methods, effective interval and proof lifetime. There is no default or parallel proof lifecycle. Self-targets require the existing ordinary sign-out path and are rejected here.

Execution uses a typed owner entry into the existing StepUp transaction. Before acquiring the actor row or Account/user locks, Identity acquires the distinct actor and target advisory session locks in ordinal order of their canonical `N` identifiers. Password sign-in retries prelock discovered previous/prior-result sessions before Account locking. Federation result retries prelock previous/result sessions in the same order. Existing one-session authenticator operations retain their actor lock and immediate source-based denial of other affected sessions; they do not acquire all those session rows.

The target must still be active, unexpired under current authentication policy, stamp-current, method-current and at the exact expected version. Reading or revoking it does not renew its activity timestamp. The local transition clears protected ticket/key material, increments the target version once, and stages its existing reference-only `TunnerSessionRevoked` outbox event with the exact owner operation/correlation. Existing StepUp verifies the actor, Account access intervals, proof/method facts and final effective policies after asynchronous work; the typed owner additionally rechecks target facts and expiry at that final decision. Target transition, consumed proof and outbox effects commit or roll back together.

`ReadResultAsync` is a separate current-actor `SESSION_REVOKE` authorization, using the same canonical locks and final currentness checks. Success requires the exact target's persisted revoked version and operation/correlation, its cleared material, an immutable consumed proof binding the original actor/target/version/context, and both exact target-revocation and proof-consumption outbox events. A consumed proof alone or another operation's revoked target never proves success. Duplicate execution reconciles those same facts; it does not execute again to discover an uncertain outcome. Missing, mismatched or unavailable evidence is not reported as applied. An independently ended/expired actor cannot use this read; future protected browser/fresh-actor recovery remains outside this increment.

Results expose only a safe target reference, prior/result version, operation/correlation and revocation time, or a sanitized error. No credentials, raw proof/key/ticket, contact value, provider-native facts or source object is returned or logged. No notification delivery or Product propagation is inferred from the local outbox event.

Focused xUnit coverage uses the already qualified `SessionListingPostgresFixture` and existing Identity provisioning. The test-local EF interceptor records successful exact session-lock acquisitions and blocks before Account acquisition with asynchronous bounded barriers. Coverage includes causal duplicate reconciliation, authorization/ownership/origin/version failures, expiry/stamp denial without target mutation, consumed-proof-only rejection, final-policy rollback, competing/opposing requests, password/federation retry lock compatibility and ordinary StepUp consumption. Synthetic federation invalid-link calls verify lock order and fail-closed behavior only; they are not provider-live authentication qualification. Tests require the explicit isolated local integration profile; discovery/skipping is not execution evidence.

## Optional private browser integration

`AddTunnerSessionRevocation` explicitly registers the browser capability with existing listing-budget, assurance, shared step-up presentation and separate session-revocation presentation sources. Missing registration leaves listing and other step-up owners unchanged. The separate publication contains 18 `account.sessions.revoke.*` semantic keys with the shared published-text provenance. It does not extend the 74 mandatory listing keys. `GET /account/sessions/revocation/options` returns only `{locale,content}`; this publication is not authorization for a target.

`POST /account/sessions/revocation/prepare` accepts exactly `{requestId,targetReference,expectedVersion}`; identifiers are GUIDs and version is a canonical positive decimal string. It independently calls the application preparation authority, derives a new server correlation and captures the exact actor, origin, target version/activity time, authentication/assurance versions and original context expiry in a dedicated protected HttpOnly Secure SameSite cookie. Repeating the identical original selection never renews expiry; rebinding its request ID to another target/version conflicts. No target, Account, proof or original cookie value goes into a URL or persistent browser storage.

Preparation and `GET /account/sessions/revocation/context` return `{requestId,operationReference,status,target:{reference,version,lastSeenAt},expiresAt}`. Status is `PENDING`, exact causal `COMPLETED`, or authoritative stale-selection `CHANGED`. A reload/provider return recovers the frozen original before UI detail-selection guards. The original owner request ID is distinct from the shared dialog request ID. Shared completion must match `operationReference` and then read the exact owner result.

The shared proof browser uses a per-request routing adapter preserving the registered/decorated fallback owner. Preparation snapshots that fallback binding so an always-present unrelated operation does not mask the selected session operation. A different subsequently selected owner takes precedence for shared proof; the original session cookie remains available for result-only reconciliation. Typed session dispatch occurs before starting the application transaction, independently of the outer fallback owner's type; it never invokes nested `RevokeAsync` inside another owner callback. Existing password/native passkey/TOTP/federation continuations share that dispatch. The existing assurance source is additionally bounded by the original browser interval/version at its existing final proof-policy decision, preserving approved values and preventing execution after original context expiry.

`POST /account/sessions/revocation/result` accepts only `{requestId}`. After independent current-actor authorization, the exact causal receipt returns `{requestId,operationReference,status:"REVOKED",target:{reference,version,lastSeenAt},revokedAt}`. Missing/unconfirmed receipt returns a sanitized error and retains the original cookie. It does not prove the request cannot still complete and does not authorize automatic reprepare/retry, substitute a fresh version, or report success from a consumed proof/generic dialog status. Query selectors, malformed/extra/duplicate JSON, wrong media/body size, foreign actor/origin, missing CSRF and invalid/stale protected context fail closed under existing BFF/JSON/authentication protections. The technical small JSON envelope is 4096 bytes; no production policy/page-count default is introduced.
