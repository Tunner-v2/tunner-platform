# P1 engineering environment configuration

TUN-P1-016 implements Document 06 sections 1, 4, 5, 13 and filesystem portability through the existing Platform assembly and explicit ITunnerModule registration. Canonical Drive Document 06 was fetched on 2026-10-05. The earlier authority pass omitted that approved environment/configuration contract. No new AMD or deployment decision is needed for this technical foundation.

## Contract and composition

An immutable EngineeringEnvironmentConfiguration snapshot reads the explicit `Tunner:EngineeringEnvironment` section through the existing Microsoft.Extensions.Configuration framework. It contains Class, Reference, Endpoints and SecretReferences. Class must be canonical LOCAL_DEVELOPMENT or EPHEMERAL_TEST; it never defaults from ASP.NET/DOTNET environment names. SANDBOX/STAGING/PRODUCTION are Connected Product classes in Document 06 and cannot masquerade as engineering environments in this model.

Endpoints are named non-secret network URIs. The supported technical schemes cover the already selected HTTP, PostgreSQL, RabbitMQ and Redis transports. User-info, query/fragment credential carriers, control/whitespace, absent host and invalid ports are rejected. This validates syntax/separation only; it is not a network destination allowlist, dependency health check or permission to connect.

SecretReferences contains named StoreReference/ResourceReference pairs only. Neither raw secret values, bootstrap tokens nor arbitrary business-policy/runtime-state fields are accepted by the configuration section. Unknown/scalar-versus-object/malformed fields fail with constant errors that omit submitted keys and values. Operators and owning adapters must ensure opaque reference fields contain references rather than secret material; this parser cannot prove an arbitrary string is a vault reference. All real secret resolution requires the approved ISecretStore abstraction and workload authorization; no store adapter or resolver is implemented here.

EngineeringEnvironmentModule implements ITunnerModule. An explicitly activated module validates configuration before registering one immutable singleton. Duplicate registrations fail. The host's existing configuration providers determine precedence; this capability neither reads global environment variables itself nor installs providers, reads local files automatically or silently reloads a snapshot. Register with `builder.Services.AddTunnerModules(new EngineeringEnvironmentModule(builder.Configuration));` at the owner-selected composition boundary. P1-002's existing API/Worker placeholders continue to activate only their explicitly selected modules; this foundation does not activate dependencies or new startup side effects.

Code contains protocol/schema rules only. Deploy-time values live in an explicit credential-free `infra/environments/engineering.example.json` or runtime configuration. No business policies, Product identities/residency, credentials, secret injection, cloud infrastructure, release promotion, live dependency connections, health expansion or production readiness are implemented. The example matches the existing local Docker host ports: PostgreSQL 25432, RabbitMQ AMQP 25672, Redis 26379 and OpenBao 28200, with reference placeholders. Document 06 section 7 permits conflict-driven local overrides; conventional container-internal ports remain unchanged. Configuration providers can override an endpoint without a source change. Paths are resolved at runtime and no machine-specific checkout path is persisted.

## Tests and security review

Execute tests for missing/invalid engineering identity; separation from Product classes; endpoint credential/query/fragment and malformed shape rejection; reference-only secret records; redacted errors; immutable snapshots and duplicate module registration; case-insensitive .NET keys and ordered provider precedence; JSON example loading; runtime configuration override and repository-root independent loading. Include real Generic Host composition without starting a process or resolving a secret. Existing 76 architecture cases remain regression coverage, including host, OpenAPI, provider, policy and authorization boundaries.

Threat boundaries: operator configuration can select a destination/reference; authorization and destination policy remain with the owning adapter. No caller is authorized by an environment label or secret reference. No config enumeration is logged, and rejected data is not included in exceptions. An immutable snapshot requires explicit reactivation for new configuration; there is no invisible configuration-driven identity change.
