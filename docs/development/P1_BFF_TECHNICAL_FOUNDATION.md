# P1 User/Admin BFF technical foundation

TUN-P1-019 implements the existing P1-BFF-001 boundary from Documents 01/02, the session contract in Document 17 section 8, separate workforce authority in Document 28 section 11, and accepted ADR-0004/0005/0006. Current Drive readback and FigJam sections 36/40/41 agree. This is the planned technical cookie/security foundation, not an Identity, Account, workforce login or Product API implementation. No new AMD or public domain contract is created.

## Composition and activation boundary

Use separate ASP.NET Core composition roots in src/Tunner.User.Bff and src/Tunner.Admin.Bff. Each reuses Platform modules, Observability redaction and a cohesive Platform/Bff capability. The only shipped route is technical /health over HTTPS. No login/logout, token, CSRF-bootstrap, projection, generic proxy, content service or realtime route is published. Tests add explicitly synthetic endpoints only inside their isolated test hosts. The frontend and existing API/Worker remain unchanged.

Framework cookie authentication and ITicketStore provide the shared mechanics. Cookie names, schemes and stable Data Protection application names differ by surface. Session cookies are Secure, HttpOnly, SameSite=Lax, host-only and path=/ with __Host- names; antiforgery cookies use Strict. Names/discriminators never depend on checkout location. All non-health requests require an explicit Bff:BrowserOrigin HTTPS origin and matching request host; missing origin fails closed. Supplied Origin must match, and unsafe methods require it. Forwarded headers and CORS are not enabled. Direct TLS is required; a later trusted-proxy/deployment contract must be explicitly reviewed before introducing a proxy exception.

The default ITicketStore accepts no identity and cannot create or renew a ticket. Real sign-in is explicitly disabled by the cookie event even if a store is accidentally registered. No lifetime, assurance, idle/renewal policy, external login or role mapping is invented. ExpireTimeSpan=Zero removes the framework's implicit lifetime; sliding renewal is disabled. A retrieved ticket must carry explicit unexpired issuance/expiry and an authenticated identity bound to its surface scheme. Every authenticated request rechecks the server store. No principal/token body is serialized into a browser cookie when SessionStore is used.

Identity/workforce owners must later supply the authoritative server store, current Account/workforce restrictions, expiry/idle/assurance/policy validation, revocation and explicit authentication/session rotation under their approved work. Activating the disabled sign-in event is a governed owner change. ITicketStore is not a substitute for the domain TunnerSession registry or its policy. P1 does not assert implemented registration, authentication ceremony, rotation or multi-Product sign-out. Separate cookie protection is not process isolation against a compromised server or shared machine account.

## Request controls

Default and fallback authorization require the surface cookie scheme. Unauthenticated/forbidden requests return safe 401/403 Problem Details without login/return-URL redirects. Reuse P1-017 TechnicalProblemDetails and canonical error classes with server-generated correlation and an opaque UNSPECIFIED retry classification; this conveys no retry permission. Transport/origin/CSRF failures reveal no submitted headers, cookies, URLs or exceptions.

All unsafe methods are checked explicitly through framework IAntiforgery.ValidateRequestAsync, including DELETE and anonymous endpoints. A single X-Tunner-CSRF request header and the matching cookie are required. SameSite is defense in depth. Health's narrowly marked GET/HEAD exemption never grants a general AllowAnonymous bypass. Responses are no-store/nosniff. Exception handling emits a constant technical problem; default unredacted logging providers are removed before registering existing Observability redaction.

No new TLS certificate, key file, store connection, secret, deployment port or production policy is committed. A host may serve HTTPS health while browser origin/session integration is unconfigured; browser operations remain denied. Set Bff:BrowserOrigin through runtime configuration when an approved UI origin is known. Obtain certificates/key-ring protection and deployment approval through the environment owner. Startup commands are dotnet run --project src/Tunner.User.Bff or src/Tunner.Admin.Bff with runtime HTTPS configuration; repository recovery remains tunner context build.

## Primary implementation research

[ASP.NET Core cookies](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/cookie?view=aspnetcore-10.0), [ITicketStore](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.authentication.cookies.iticketstore?view=aspnetcore-10.0) and [SessionStore](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.authentication.cookies.cookieauthenticationoptions.sessionstore?view=aspnetcore-10.0) support framework server-ticket storage and per-request identity validation. [Data Protection configuration](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0) supports explicit application separation. [ASP.NET antiforgery](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0) and [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) support explicit unsafe-method validation and combined origin/token defenses. These sources inform implementation; Tunner authority owns policy and activation.

Windows TLS fixture note: Schannel cannot use the initial ephemeral key directly (see [dotnet/runtime issue 93319](https://github.com/dotnet/runtime/issues/93319)). The fixture imports its generated PKCS12 buffer using DefaultKeySet without PersistKeySet, scrubs the buffer, pins the exact certificate and disposes it after all listeners stop. Windows may use a temporary user key container that .NET removes on disposal; no trust-store installation or persistent key/certificate is requested. This affects test setup only.
