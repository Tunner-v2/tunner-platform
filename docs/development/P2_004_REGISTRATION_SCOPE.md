# P2-004 Registration and verified-contact activation scope

Implement the existing FRD17/31 registration and email-proof workflow through the User BFF and Accounts/Identity store. New accounts remain VERIFICATION_PENDING until server age eligibility, valid contact proof, current policy and uniqueness gates permit ACTIVE. Existing Accounts are never duplicated or silently linked. Anonymous response shape and work must not reveal Account existence. Duplicate requests replay the same operation; versioned mutation rechecks state and uniqueness atomically. No authenticated session or Product membership/entitlement is created.

The existing editable Figma registration/verify/result frames require FRD alignment before affected flow implementation: DOB in place of unnecessary full name, no GitHub, no automatic Product access, no screenshot-derived password or challenge expiry constants. Reuse @tunner/ui theme/content/controls. Content and legal/security notice references resolve from governed published versions, not screen-local authority.

Required effective server policy inputs include registration/age/security versions and approval provenance, password blocklist/length/hash work parameters, proof lifetime/attempt/resend and abuse limits, processing/retention references and effective notice/terms/privacy versions. Missing/ambiguous input denies processing. Numeric test values are isolated fixtures and never production defaults. Email proof is contact confirmation, not MFA or an authenticated session.

Registration, verification and resend publish safe reference-only post-commit work through the existing outbox and notification boundary. Challenge credentials never appear in an HTTP response, event payload, log or UI storage. Credential/proof data stays inside Identity and protected delivery scope. Actual provider acceptance/delivery remains separate from commit/queue state.

Expected implementation contracts: server-derived pre-registration browser context plus stable caller idempotency identity; RegisterAccount (DOB/email/password/notice references); VerifyContact (operation proof and expected version); ResendVerification (stable retry identity and expected version); public policy/content/eligibility projection for the form. No Account IDs are disclosed before the appropriate proof, no client may mark verification true, and verified-email uniqueness is rechecked in the authoritative transaction.

Required validation includes real PostgreSQL concurrent registration/verification, replay/expiry/attempt/resend limits, missing policy, age/privacy/minimization, state/outbox atomicity, framework credential round trip, BFF HTTPS/origin/CSRF/anonymous boundaries and accessible responsive browser states. Mandatory final role reviews and exact-SHA ownership evidence precede readiness. Product acceptance and release/security gates remain separate.

User-directed sequencing clarification (2026-10-16): the first screen collects email/password and terms/privacy acknowledgement only. Continue opens a separate DOB eligibility step; no registration request or Account mutation occurs before that step succeeds. Terms/privacy acknowledgement is not age evidence. The user explicitly chose this later eligibility step. FRD17 section11 and PDR-0007 require DOB during registration, not on the first screen; their server 18+ gate remains unchanged. The existing editable Figma first screen was updated before code, with new eligibility frame 187:2.
